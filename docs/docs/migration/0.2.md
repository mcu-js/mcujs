# Migrating from MCU.js 0.1 to 0.2

MCU.js 0.2 deliberately replaces first-backend accidents with a portable contract for RP2040, RP2350, and ESP32-S3. This page describes the target 0.2 contract; check the firmware version and `board.apiVersion` before using APIs that have not reached a released image yet.

The detailed rules are in the [portable API contract](../api-design/portable-api-contract.md), with the machine-readable schema published at [/schemas/mcujs-portable-api-0.2.schema.json](/schemas/mcujs-portable-api-0.2.schema.json).

## Replace board sniffing with feature detection

In 0.1, examples often selected pins or APIs with `board.name` or `board.chip`. Keep those fields for diagnostics, not compatibility branches.

```js
// 0.1 pattern: do not carry this into portable code.
if (board.name === 'pico') {
  // Pico-specific assumption
}
```

Use the module registry, capability metadata, semantic pins, and onboard inventory instead:

```js
(function () {
  var boardApi = require('board');
  var modules = require('mcujs:module');

  if (boardApi.devices.led) {
    var led = boardApi.devices.led;
    var gpioCapability = boardApi.capability('gpio');
    if (led.type === 'gpio' && gpioCapability &&
        gpioCapability.pins.indexOf(led.pin) !== -1) {
      var gpio = require('gpio');
      gpio.init(led.pin, gpio.OUTPUT);
      gpio.set(led.pin, !led.activeLow);
    } else {
      boardApi.led(true);
    }
  }
}());
```

## Use canonical lower-case modules

The 0.2 documentation uses:

```js
var gpio = require('gpio');
var pwm = require('pwm');
var adcApi = require('adc');
var i2c = require('i2c');
var spi = require('spi');
var pixels = require('neopixel');
var boardApi = require('board');
```

The 0.1 globals `GPIO`, `PWM`, `adc`, `I2C`, `SPI`, `neopixel`, and `board` remain compatibility aliases through the 0.x series when the corresponding capability exists. In exact schema notation these include `global.adc` and `global.neopixel`. They are not portable names and may be removed no earlier than 1.0 with migration notes.

## Detect optional APIs by absence

0.2 removes unsupported stubs and no-op shortcuts:

- unavailable modules are absent from `builtinModules` and return the normal module-not-found failure from `require()`;
- unavailable optional methods and properties are absent;
- `board.led()` and `board.neopixel()` only exist when the corresponding onboard device exists;
- an external `neopixel` module may still exist when `board.devices.neopixel` is absent.

Do not catch every `require()` failure to guess whether a feature exists. Use `require('mcujs:module').has(name)` first so spelling and module-load bugs remain visible.

`require('board')` is now canonical and returns the same object as the legacy
global `board` alias. Its `apiVersion`, semantic `pins`, physical `devices`, and
capability descriptors are immutable discovery data. Use
`board.capability(name)` in ordinary programs: it materializes only one frozen
descriptor. Reserve the larger `board.capabilities()` snapshot for diagnostics
and tooling on heaps that can afford the complete registry.

0.2 also removes the old implicit “full RP runtime” build default. Every RP2040,
RP2350, and XIAO ESP32-S3 image now selects a closed feature map. The same
descriptor generates native registration, REPL help, runtime discovery, and the
board-qualified `mcujs-<version>-<board>.capabilities.json` release manifest.
This reports what the firmware actually enables, not everything the MCU could
theoretically support.

## Use semantic pins and declared routes

Replace hard-coded GPIO numbers with `board.pins` when a semantic alias exists. For bus wiring, use the descriptor's `defaultBus` and `defaultRoute`, or an explicit route listed by `board.capability('i2c')` or `board.capability('spi')`. `defaultRoute` is one complete listed route whose bus equals `defaultBus`, so omitted pins remain deterministic even when the default bus has multiple valid routes.

Only safe, physically exposed pins appear in these maps. Silicon-valid internal, flash, PSRAM, USB, or strapping pins are not portable GPIO.

## Reinitialize GPIO after peripheral takeover

GPIO writes no longer accept truthy/falsy substitutes. Pass only `true` or
`false`; numeric `0`/`1` now throw `TypeError`. Pins and modes must also be
finite, integral, and listed by `board.capability('gpio')`.

Every `gpio.set()`, `gpio.get()`, and `gpio.toggle()` now requires a successful
`gpio.init()` on every backend. PWM and routed peripherals may take over a GPIO
soft claim, but stale GPIO state cannot access the pin afterward. Once that
peripheral releases the pin, initialize GPIO again explicitly:

```js
var gpio = require('gpio');
var pwm = require('pwm');
var pin = require('board').capability('pwm').pins[0];

gpio.init(pin, gpio.OUTPUT);
gpio.set(pin, true);
pwm.init(pin, 1000);       // deliberate GPIO -> PWM takeover
// gpio.set(pin, false);   // ResourceBusyError, code === 'EBUSY'
pwm.stop(pin);
gpio.init(pin, gpio.OUTPUT); // explicit recovery of GPIO ownership/config
gpio.set(pin, false);
```

An active PWM or bus claim remains exclusive; GPIO cannot silently remux it.
Failed RP multi-pin takeover attempts release only the claims acquired by that
attempt and leave GPIO inaccessible until explicit reinitialization.

## PWM duty is now only a ratio

The 0.1 implementations accepted backend-specific raw PWM values such as `0..65535`, and some accepted both raw and ratio forms. In 0.2, `pwm.setDuty(pin, duty)` accepts only a finite ratio from `0..1`.

```js
// 0.1 raw duty
PWM.setDuty(pin, 32768);

// 0.2 portable ratio
var pwm = require('pwm');
pwm.setDuty(pin, 0.5);
```

Values outside `0..1` throw `RangeError`; they are not clamped or reinterpreted.
For a legacy 16-bit raw value, the mechanical conversion is
`ratio = raw / 65535`. The resulting ratio must still be representable exactly
by the period selected for that pin and frequency; otherwise `setDuty()` throws
`NotSupportedError` with `code === 'ERR_NOT_SUPPORTED'` rather than rounding.

PWM frequencies now have the same strict split. A frequency outside the board's
advertised range throws uncoded `RangeError`; an in-range frequency that cannot
be represented exactly throws `ERR_NOT_SUPPORTED` without changing an existing
waveform. Read `board.capability('pwm').maxOutputs` and `.timerCount` instead of
assuming backend channel counts. Same-frequency outputs may share a timer,
while conflicting shared-timer configurations throw `EBUSY` and exhausted
output or timer pools throw `ERR_RESOURCE_EXHAUSTED` with a numeric `limit`.

Successful same-pin `pwm.init()` reinitialization resets duty to zero.
`pwm.stop()` drives low, releases the output, and releases a shared timer only
after its final output stops. Reinitialize GPIO explicitly before using the pin
again; peripheral release does not restore stale GPIO configuration.

## Prefer options-object bus initialization

The positional forms remain through 0.x for migration, but portable code uses `i2c.init(options)` and `spi.init(options)`. Omitted pins select the board-declared `defaultRoute` rather than a board-name table in JavaScript. Supplying another bus requires an explicit listed route.

```js
(function () {
  var i2c = require('i2c');
  var spi = require('spi');

  i2c.init({ bus: 0, frequency: 400000 });
  spi.init({ bus: 0, frequency: 1250000, mode: 0 });
}());
```

Compatibility forms:

- `i2c.init(bus, sda, scl, frequency)` → `i2c.init(options)`;
- `spi.init(bus, sck, mosi, miso, frequency)` → `spi.init(options)`.

Every address, byte, route, transfer length, and frequency is validated strictly. Maximum transfer sizes come from the capability descriptor; oversized transfers throw instead of being truncated. Current RP SPI descriptors advertise 256 bytes, while the ESP32-S3 polling/no-DMA backend advertises 64 bytes. Read `board.capability('spi').maxTransferBytes` instead of inferring the limit from a board name. Use the non-destructive [SPI loopback and logic-analyzer protocol](../development/spi-loopback-protocol.md) to verify exact bytes, maximum/max+1 rejection, mode timing, and route lifecycle.

## Use strict external NeoPixel options

The 0.2 external module uses one portable options-object form on RP2040, RP2350,
and ESP32-S3:

```js
(function () {
  var boardApi = require('board');
  var modules = require('mcujs:module');
  if (!modules.has('neopixel')) return;

  var limits = boardApi.capability('neopixel');
  var pixels = require('neopixel');
  pixels.init({pin: limits.pins[0], length: 1, order: limits.orders[0]});
  pixels.setPixel(0, 255, 0, 0);
  pixels.show();
}());
```

Do not infer external-driver availability from `board.devices.neopixel`. That
device entry and `board.neopixel()` exist only for physically onboard pixels;
the external `neopixel` module may remain available when both are absent.

`pin`, `length`, pixel index, and RGB components are now finite strict integers.
Color components are `0..255`, the index is bounded by the configured length,
and the strip length is `1..board.capability('neopixel').maxLength`. Unknown
option keys, unadvertised pins, unknown or lowercase order aliases, zero length,
and `maxLength + 1` throw rather than being coerced, wrapped, or truncated.
`order` defaults to `GRB`; explicit values must come exactly from
`board.capability('neopixel').orders`.

Use before initialization and pin contention now throw stable `EBUSY` errors.
Waveform or pixel-buffer exhaustion throws `ERR_RESOURCE_EXHAUSTED`, unsupported
native configurations throw `ERR_NOT_SUPPORTED`, and generic native failures
throw `EIO`. Successful reinitialization releases the old pin; failed argument
validation or contention does not destroy the working strip. Reinitialize GPIO
explicitly after NeoPixel releases a pin because stale GPIO configuration is not
restored.

The [NeoPixel electrical and runtime acceptance protocol](../development/neopixel-hardware-protocol.md)
covers exact maximum/max+1 behavior, known RGB/GRB colors and photographs,
power/level-shifting guidance, pin ownership, and watchdog/USB health.

## Replace RP-only ADC constants

The 0.1 RP runtime exposed `adc.TEMP` and `adc.VSYS` magic constants. They are compatibility-only and not portable in 0.2 because ESP32-S3 exposes temperature and supply rails differently.

Use:

- `adc.readTempC()` only when `board.capability('adc').temperature.supported` is true;
- `board.capability('adc').channels` and aliases such as `A0` to select an input;
- `board.capability('adc').vsys` to learn whether a VSYS measurement exists;
- `readVoltagePin()` or `readVoltageChannel()` only when `voltage.supported` is true.

Voltage is always returned in volts and temperature in degrees Celsius. The
`voltage.calibrated` flag reports whether the backend uses a calibration driver;
it never changes volts into millivolts. Raw `readPin()` and `readChannel()` values
are bounded by `0..(2^resolutionBits - 1)`. An advertised ADC capability always
contains at least one exposed pin and channel, so both required raw operations
have a valid portable input. Voltage and temperature methods use the schema's
`capabilityField` availability discriminator and are absent when their
respective support field is false. Voltage results are bounded by the advertised
`voltage.minVolts..voltage.maxVolts` range; the schema exposes these result
limits through `maximumFromCapabilityBitWidth`, `minimumFromCapability`, and
`maximumFromCapability`.

RP firmware retains `adc.TEMP === 4` when
`temperature.rawChannel === true`, and retains `adc.VSYS === 3` only when
`adc.vsys === true`. These are deprecated nonportable 0.x aliases for
`readChannel()`, not members of the five-method portable surface. Their internal
channels are intentionally not external `capability.channels` entries. An
external RP GPIO29/A3 route may independently appear as channel 3 on boards that
physically expose it; do not confuse that route with an advertised VSYS/3 path.
ESP32-S3 exposes neither property and uses `readTempC()` for its separate
temperature sensor.

Use the [ADC voltage and temperature acceptance protocol](../development/adc-voltage-protocol.md)
to verify calibrated/nominal conversion, first/last routes, temperature, and
safe pin takeover on hardware.

## Keep capability-gated compatibility extensions explicit

MCU.js 0.2 does not silently erase live 0.1 methods merely because they are not portable. It inventories them as nonportable compatibility extensions with capability-based availability:

- RP firmware may expose `spi.writeBufferDMA(bus, bufferHandle, byteLength)` when `spi.dma` is true and `spi.compatibilityExtensions` contains `writeBufferDMA`. The graphics buffer handle is an RP display-stack accident, so portable SPI code must not depend on it. In 0.2 an unknown or stale handle throws `RangeError`; `byteLength` is bounded by the handle's live byte length through `maximumFromArgumentResource`; the exact maximum succeeds and maximum+1 throws `RangeError` instead of being silently clamped. Use before `spi.init()` throws `EBUSY`; DMA-channel exhaustion throws `ERR_RESOURCE_EXHAUSTED`.
- Firmware with persistent boot-script recovery may expose `board.safeMode()` and `board.safeMode(enabled)` when `boot.safeMode` is true. The getter returns the current dynamic state; the setter persists a strict boolean. `board.safeMode(false)` during the active boot qualification window throws `EBUSY`; persistence failure uses `EIO` in the 0.2 contract.

Feature-detect these methods and capability fields. Do not branch on RP, ESP32-S3, `board.name`, or `board.chip` to infer them.

SPI initialization remains byte-oriented in 0.2. Both options and positional forms implicitly use 8-bit words and MSB-first order; manifests must advertise exactly `bitsPerWord: [8]` and `bitOrders: ['msb']`. These format values are not selectable in 0.2, so a manifest must not advertise unreachable 16-bit or LSB-first configurations.

## Update onboard-device shortcuts

Move from flat compatibility properties to `board.devices`:

| 0.1 compatibility name | 0.2 portable source |
|---|---|
| `board.ledPin` | Check `board.devices.led`, then use `board.led()`; only `type === 'gpio'` descriptors have `.pin` |
| `board.neopixelPin` | `board.devices.neopixel.pin` |
| `board.neopixelLength` | `board.devices.neopixel.length` |

Check the device key before reading it. Absence is the answer; there is no `-1` or fake pin.

Existing onboard shortcut call shapes remain available when the device exists. `board.led()` returns the current logical boolean state; `board.led(on)` remains the setter. `board.neopixel()` continues to accept one color as `[r, g, b]` or `{r, g, b}`, and multiple colors as arrays of either shape.

Do not pass every legacy `board.ledPin` value to GPIO. Some onboard LEDs are managed behind a wireless controller or another non-MCU transport. Their 0.2 descriptor is `{type: 'managed'}` and intentionally has no `.pin`; `board.led()` is the transport-neutral control surface.

One 0.1 behavior is deliberately stricter: an oversized NeoPixel color array or multi-pixel list now throws `RangeError`. Older firmware silently ignored color bytes after the first three and pixels after `board.neopixelLength`; 0.2 never truncates them. Compare a multi-pixel list with `board.devices.neopixel.length` before calling the shortcut.

## Handle stable operational errors

0.1 frequently surfaced generic `Error` messages. In 0.2, programming errors remain `TypeError` or `RangeError`, while operational errors have stable `.code` values:

The shared native validator is now wired into the RP and ESP `gpio`, `pwm`,
`adc`, and `i2c` handlers. Those migrated paths reject missing required values, non-finite
numbers, fractional integers, truthy/falsy substitutes for booleans, invalid
bytes, oversized byte arrays, and values outside their implemented ranges
before native conversion or resource-state checks. Indexed byte-array accessor
exceptions also propagate unchanged. Update code that depended on coercion,
truncation, wrapping, clamping, or state masking an invalid argument. See the
[error reference](../api-design/errors.md) for the class, code, diagnostic
properties, and current rollout boundary.

The I2C options-object form and descriptor-driven route enforcement are implemented in the production RP and ESP bindings. The SPI options-object form now follows the same production rule. Omitted pins resolve through each board descriptor's `defaultBus` and `defaultRoute`; explicit pins must match one complete listed route. Positional forms remain available through 0.x for migration. SPI mode defaults to 0 and must be advertised, while 8-bit words and MSB-first order are fixed rather than selectable. The external NeoPixel options, limits, order, ownership, and operational-error contract is also implemented in both production backends; timers and other optional handlers remain capability-gated independently.

Unlisted routes or modes and frequencies outside the advertised range throw `RangeError`. `ERR_NOT_SUPPORTED` starts only after every explicit argument constraint passes, for example when an in-range frequency cannot be represented exactly by the hardware.

```js
try {
  // Use an initialized peripheral.
} catch (error) {
  if (error instanceof RangeError) {
    console.log('Choose an advertised route or mode and an in-range frequency');
  } else if (error.code === 'EBUSY') {
    console.log('Resource is temporarily unavailable');
  } else if (error.code === 'ERR_NOT_SUPPORTED') {
    console.log('Valid request cannot be represented exactly by this hardware');
  } else {
    throw error;
  }
}
```

Also expect `ERR_RESOURCE_EXHAUSTED`, `ENXIO`, and `EIO`. The API stays present for all of these operational failures.

## Pre-1.0 policy

A 0.x minor may deliberately break accidental behavior, but every minor has a frozen, documented schema. A patch does not change the 0.2 contract. Compatibility aliases listed in the schema remain through 0.x and may be removed no earlier than 1.0. Every deprecation or removal must include migration notes.
